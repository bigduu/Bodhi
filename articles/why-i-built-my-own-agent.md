# 我为什么决定自己写一个 Agent

过去这段时间，Agent 这个方向越来越热。

从 OpenAI 的 Codex，到 Anthropic 的 Claude Code，再到 OpenClaw 这样的开源替代方案，几乎所有人都在试图回答同一个问题：

**下一代开发工具，到底会不会从"编辑器 + 模型"演化成"真正可以工作的 Agent"？**

我对这个问题的答案一直是肯定的。

我也一直在用这些产品，观察它们，拆它们，理解它们。但越看，我越有一种强烈的感觉：

**我并没有真的等到那个我想要的 Agent。**

---

## 为什么我对现有 Agent 不满意

先说清楚一点：我并不否认这些产品的价值。恰恰相反，我对它们的关注越深，越能感受到它们推动了整个 Agent 方向快速前进。

但也正因为我认真看过它们，我才更明确地知道自己不满意的地方到底是什么。

### 有些产品强在"模型体验"，不在"系统设计"

很多产品已经证明了一件事：只要模型足够强，配上工具调用、终端执行和文件读写，一个 Agent 看上去就会非常惊艳。

但问题是，**"看上去像 Agent"和"本质上是一个好的 Agent 系统"不是一回事。**

我越来越觉得，一个真正可用的 Agent，不能只依赖模型能力本身。它必须在系统层面解决这些问题：

- 长任务怎么持续
- 上下文怎么压缩和保真
- 工具怎么被稳定地调用
- 危险操作怎么获得边界
- 用户怎么理解当前状态
- 专业任务怎么切换到更合适的工作模式

如果这些问题没有被系统化地解决，那无论外面包了多少"智能感"，它都更像一个高配聊天工具，而不是一个真正可以长期工作的 Agent。

### 有些开源方案的工程质量，我确实不太放心

这是一个很现实的问题。

我在看一些开源 Agent 方案时，最大的顾虑不是"它能不能跑起来"，而是"它是不是一个我愿意把工作流交给它的系统"。

当一个系统开始拥有这些能力的时候——读取本地代码、修改文件、执行命令、调用外部服务、维护长期上下文——那么工程质量、架构边界、错误处理、权限策略、状态一致性这些问题就会变得非常重要。

我不太接受一种状况：一个系统在能力上看起来已经很像 Agent，但在工程上还停留在"能跑就行"。

这也是为什么我最后更愿意自己写。因为我想做的不是一个"看起来已经够像"的系统，而是一个我自己在工程上能真正信任的系统。

### Claude Code 很强，但它不是我想要的终点

Claude Code 是目前我非常认可的一类产品。它代表的是另一条路线：把模型能力、工具体验、CLI 工作流和编码任务深度揉在一起，做成一个完成度很高的产品。

但我最后还是决定自己做，不是因为我觉得 Claude Code 不好，而是因为我想要的东西和它仍然不完全一样。

还有一个更现实的问题：**可用性。**

如果一个我非常依赖的工具，在某些地区不稳定、不可得或者受平台策略影响，那它就很难成为我真正愿意长期围绕它构建工作方式的基础设施。

这不是一个附属问题。这恰恰是"我要不要自己做"的核心原因之一。

---

## 所以我决定自己写一个

我从一开始就没打算做一个玩具，也没打算做一个 prompt demo，更没打算做一个"我也有个 AI 聊天框"的产品。

我想做的是一个真正意义上的 Agent 系统。

而且我想做的是一个**不比它们差的 Agent**。

这就是 Bodhi 的起点。

---

## 我理解的 Agent，不只是"模型 + 工具"

做 Bodhi 的过程中，我越来越确信一件事：

**Agent 真正的门槛，从来不只是模型能力。**

模型当然重要。没有足够强的模型，很多事情根本谈不上。但如果只把 Agent 理解成"模型 + 几个工具"，那最后做出来的东西，大概率只是在表层上像 Agent。

在我的理解里，一个真正可用的 Agent 至少要同时解决五件事：

1. 它能不能在长任务里保持连续性
2. 它能不能形成稳定的行动闭环
3. 它有没有一套可靠的内建操作能力
4. 它能不能既保留内核稳定性，又具备外部扩展性
5. 它能不能根据任务切换到更专业的工作模式

而这五件事，最终分别落到了五个设计主题上：

- Context（上下文）
- Agent Loop（执行闭环）
- Built-in Tools（内建工具）
- MCP（外部扩展）
- Skills（专业工作模式）

Bodhi 其实就是围绕这五件事逐渐长出来的。

---

## Context：上下文不是聊天记录，而是 Agent 的工作记忆

我做 Bodhi 的时候，最先下重手的一层就是 Context。

因为我觉得很多 Agent 对"上下文"的理解都太浅了。它们把上下文理解成"把更多消息塞进模型"，这当然有帮助，但远远不够。

一个真正工作的 Agent，面对的上下文不是单一的聊天历史，而是一个复杂得多的结构：

- 系统规则和约束
- 当前任务目标和状态
- 用户补充的偏好和上下文
- 最近的工作窗口（高保真）
- 被压缩过的历史摘要
- 长期持久化的外部记忆
- 当前工作区和环境状态
- 工具执行结果和链条
- 子任务与子会话之间的关系

我越来越不相信那种"只要 context window 足够大，一切都会自然解决"的思路。大上下文当然有价值，但它不能替代结构化的上下文管理。

所以 Bodhi 里的上下文系统，不是简单扩容，而是分层：

- 保留系统规则和当前任务
- 将最近工作窗口维持在高保真状态
- 对旧上下文进行摘要和压缩
- 尽量保证工具调用链不被粗暴截断
- 把长期稳定的信息放进外部 memory 中持久化

我真正关心的问题不是"最多能塞多少 token"，而是：

> **在有限上下文里，系统到底保留下了哪些最值得保留的信息。**

这件事会直接决定一个 Agent 在第 30 轮、第 50 轮、第 100 轮时还是不是同一个 Agent。

---

## Agent Loop：不是多轮对话，而是带边界的行动闭环

如果说 Context 决定了 Agent 是否"记得住"，那 Agent Loop 决定的就是它是否"真的动起来"。

在很多介绍里，agent loop 会被说得很轻巧：模型输出工具调用，系统执行工具，把结果喂回去，直到结束。

但一旦你真正自己实现，就会发现真正困难的部分根本不在这个抽象描述里，而在这些细节里：

- 工具参数不合法怎么办
- 某个工具连续失败怎么办
- 一轮中调用太多工具怎么办
- 什么时候应该继续循环，什么时候应该终止
- 什么时候应该把错误反馈给模型，什么时候应该直接拦住
- 什么时候要等待用户审批或输入
- 当模型过于激进时，系统怎么给它边界

这也是我为什么一直不把 agent loop 理解成"自动多轮对话"。对我来说，它本质上更像一个**带边界的行动执行器**。

Bodhi 的很多设计，其实都是围绕一句话展开的：

> Agent 要足够自主，但不能失去边界。

所以我会特别强调这些机制：

- **权限申请**：模型在执行高风险操作前，必须向用户请求明确授权
- **审批停顿**：遇到写文件、执行命令等操作时，agent loop 会暂停等待确认
- **交互式提问**：当信息不足或需要用户判断时，系统会结构化地发起提问
- **任务状态追踪**：每一轮执行结束后，系统会评估任务进度并更新状态
- **调用上限和熔断**：每轮工具调用有上限，单个工具连续失败会触发熔断
- **结论确认**：在输出结束前，会要求模型带着结构化总结向用户做最终确认

这些东西表面上看像 UX 细节，但本质上它们都属于 agent loop 的一部分。

因为一个真正可用的 Agent，不能只是"会继续跑"。它必须知道：

- 什么时候该继续
- 什么时候该停
- 什么时候该问
- 什么时候该交还控制权

---

## Built-in Tools：Agent 的下限，取决于它的内建能力

我对 built-in tools 的看法一直很明确：**它们不是附属功能，而是 Agent 的地基。**

很多人一提 Agent，就容易先想到外部生态、第三方集成、联网能力、插件市场。这些当然重要，但如果一个 Agent 连最基础的这些事都做不好——

- 读文件、搜目录、查代码
- 精确编辑、执行命令
- 请求权限、更新任务状态
- 维护持久记忆
- 向用户发起结构化确认

那它其实还没有建立起真正的"系统能力"。

而且我越来越觉得，工具系统的关键不只是"有没有"，而是：

- schema 清不清楚
- 参数稳不稳定
- 返回值是否结构化
- 权限是否明确
- 使用规范有没有被注入给模型
- 模型会不会被引导到正确的调用方式上

很多 Agent 看上去工具很多，但一到复杂任务，模型其实并不知道该怎么可靠地使用它们。

所以 Bodhi 做的一件非常重要的事，不只是"提供工具"，而是**提供工具 + 提供工具使用规则**。

每一个内建工具，都有配套的使用指南（tool guide）。这些指南会在运行时被注入到上下文中，告诉模型：

- 这个工具什么时候该用
- 什么时候不该用
- 参数应该怎么传
- 常见的错误调用模式是什么

在我看来，这是 built-in tools 真正能成为系统能力的前提。

---

## MCP：扩展边界很重要，但不能拿它代替地基

MCP 这件事，我是很认同的。它几乎是现在 Agent 生态里最关键的一种扩展接口之一。

有了 MCP，Agent 才能真的去连接外部世界——接入第三方服务、私有系统和更多专门能力。

但我做 Bodhi 时一直有一个判断没有变：

> **MCP 应该负责扩展边界，而不是替代内核。**

如果一个 Agent 连自己的核心操作能力都不稳定，全靠外部扩展去补，那它会面临一堆问题：行为不可预测、延迟和稳定性不一致、调试成本高、权限边界模糊。

所以在 Bodhi 里，我更倾向于一种双层结构：

- **Built-in Tools 负责核心基础能力**
- **MCP 负责外部能力扩展**

这意味着 Bodhi 既不是一个封闭系统，也不是一个只会把问题外包给插件生态的壳。它更像是一个有自己内核、同时又愿意向外生长的 Agent。

---

## Skills：我不想让 Agent 每次都从零开始扮演专家

Skill 也是 Bodhi 里我很重视的一层。

在很多系统里，所谓 skill 更像是一种 prompt 包装。但我做着做着越来越不满意这种理解。因为如果 skill 只是 prompt 模板，那它最终很容易变成一组松散的"专家人格文本"，而不是稳定的工作模式。

我更愿意把 skill 理解成一种**显式的专业工作模式**。

做 Jira，是一种模式。做 Confluence，是一种模式。做文档、做代码分析、做 UI 设计、做文件处理，都是不同的模式。

一个好的 skill 系统，不应该只告诉模型"你现在是谁"，而应该同时告诉它：

- 这类任务的边界是什么
- 这类任务优先使用什么工具
- 哪些资源要先加载
- 输出应该遵循什么结构
- 哪些行为不应该发生

我想做的不是一个"什么都懂一点"的 Agent。我更想做一个**在不同任务面前，会切换到更合适工作模式的 Agent**。

---

## Bodhi 和其他 Agent 产品到底有什么不同

如果非要把 Bodhi 放进一张横向图里，我觉得它和 Codex、Claude Code、OpenClaw 的区别，不在"谁更强"这种单一结论上，而在于它们分别站在哪条路线上。

### 四条不同的路线

**Codex** 走的是"模型原生"路线。它把 OpenAI 最强的编码能力直接包装成一个 agent 产品，强在模型推理和代码理解，但系统层面对用户来说基本是个黑盒。

**Claude Code** 走的是"产品完成度"路线。它把模型能力、工具流、终端体验和编码场景深度揉在一起，CLI 交互做得非常成熟。但它是 Anthropic 体系内的产品，在地区、平台和可控性上存在天然限制。

**OpenClaw** 走的是"开源替代"路线。它试图用开源方式复刻 Claude Code 的体验，让更多人在自己的环境里用起来。方向有价值，但不同开源项目之间的工程质量、架构边界和系统完成度差异非常大。

**Bodhi** 走的是另一条路：一个本地优先、强调系统设计、强调可控性和长期工作的完整 Agent 系统。

### 逐维度对比

| 维度 | Codex | Claude Code | OpenClaw | Bodhi |
|---|---|---|---|---|
| **产品定位** | 模型原生能力强的 coding agent | 产品完成度极高的 CLI coding agent | 开源 Claude Code 替代方案 | 本地优先的完整 Agent 系统 |
| **技术栈** | Node.js + OpenAI API | Node.js + Anthropic API | Node.js / Electron + Web | Rust 后端 + Tauri 桌面 + React 前端 |
| **上下文压缩策略** | 模型驱动 compact：用模型自己生成摘要替换历史，保留最近用户消息（≤20k tokens），支持 mid-turn 压缩 | 有 CLAUDE.md / memory 文件机制，偏手动管理 | 基本依赖原始对话窗口，无显式压缩 | 混合策略：LLM 摘要 + 启发式摘要 + 工具链原子保护 + 外部持久记忆 |
| **压缩触发机制** | 自动：上下文超限时自动触发 compact 任务 | 半自动：用户可手动触发，也有自动摘要 | 无 | 多种触发：截断时触发、周期性触发、token 阈值触发 |
| **压缩后的历史结构** | 保留用户消息 + 摘要作为 user message 插入；可重新注入 initial context | memory 文件持久化，对话历史可被压缩 | 无结构化处理 | 分层保留：系统规则 → 摘要 → 最近窗口 → 持久记忆，每层有独立 token 预算 |
| **工具链保护** | 有 TruncationPolicy，工具输出可被截断 | 有基本的工具输出处理 | 通常无特殊保护 | 工具调用链原子保护：tool call 和 tool result 作为整体段，不会被从中间截断 |
| **Agent Loop** | 强，但偏产品黑盒 | 强，有 permission/hook 机制 | 取决于具体实现 | 自定义 loop + 审批 + 熔断 + 任务评估 + 结论确认 |
| **内建工具** | 强，偏编码场景 | 强，偏终端和文件操作 | 通常较薄，依赖外接 | 20+ 内建工具 + tool guide 注入 + 严格参数校验 |
| **工具使用引导** | 模型自行判断 | 模型自行判断 + command | 模型自行判断 | 工具使用规范显式注入上下文，引导模型正确调用 |
| **权限控制** | 有 sandbox / approval 机制 | 有 permission hook | 通常较基础 | 6 种权限类型 + 主动权限申请 + 风险等级标注 + 审批卡片 |
| **MCP 支持** | 有生态但可控性受限 | MCP 支持强，是原生能力 | 通常兼容 | 内建地基 + MCP 扩展，双层结构 |
| **Skills / 专业模式** | 无显式系统 | 偏 slash command | 无显式系统 | Skill 是显式工作模式，含触发匹配、资源加载、行为约束 |
| **子会话 / 并行** | 有 subagent 概念 | 有 subagent / Task 机制 | 通常不支持 | 完整子会话生命周期：创建、运行、重试、删除、历史追溯 |
| **定时 / 调度** | 无 | 无 | 无 | 内建 schedule_tasks，支持周期性自动执行 |
| **本地可控性** | 有限，依赖 OpenAI 生态 | 受地区和平台限制 | 较开放，但依赖社区维护 | 强调本地优先：所有数据在本地，支持多模型接入 |
| **工程可理解性** | 产品黑盒 | 产品黑盒 | 开源但质量参差 | 自己掌控全栈：后端框架 + 前端 + 桌面壳，959+ 测试 |

### 特别展开：上下文压缩，Codex 和 Bodhi 的思路差异

上下文压缩是我特别想展开对比的一个维度，因为它很能说明两个系统在设计哲学上的不同。

**Codex 的做法很"模型原生"。**

我看了 Codex 的源码。它的压缩核心是一个叫 compact 的机制：当上下文快要超限时，系统会自动把当前历史喂给模型，让模型自己生成一段"交接摘要"（handoff summary）。然后把这段摘要作为 user message 插入，配合最近保留的几条用户消息（上限 20k tokens），替换掉之前的历史。它甚至支持 mid-turn compaction——在一轮执行中间就能触发压缩，而不用等到这轮结束。

这个做法很聪明，因为它把"怎么压缩"这件事交给了最理解当前对话的模型本身。但它也有一个很明显的特点：**压缩质量高度依赖模型能力**。模型生成的摘要好不好，直接决定了下一轮 agent 还能不能接着干活。

Codex 还有 Memories 系统，用两阶段流水线从历史 rollout 里提取持久记忆，这个思路也很好。但它的核心压缩动作——"让模型自己写摘要然后替换历史"——本质上还是把信任交给了模型。

**Bodhi 的做法更"工程化"。**

我没有完全依赖模型来做压缩。Bodhi 用的是混合策略：

- 有一套**启发式摘要器**，不调模型，直接从历史里提取用户问题、使用的工具和关键结论。成本低、速度快、不依赖模型当次表现
- 同时也有**LLM 摘要器**，在条件允许时调用模型生成更精细的摘要，但如果调用失败会自动 fallback 到启发式摘要
- 更重要的是，Bodhi 对**工具调用链做了原子保护**：一个 tool call 和它的 tool result 被视为一个不可分割的段，压缩时要么整体保留，要么整体丢弃，不会出现"保留了工具调用但丢掉了返回结果"的情况

这件事看起来小，但在实际使用中非常重要。因为一旦 tool call 和 tool result 被拆散，模型在下一轮就会基于不完整的信息做决策，很容易出错。

**所以归根结底，差异不在"谁压缩得更多"，而在"压缩之后，agent 还能不能正确工作"。**

Codex 把这件事主要交给模型判断；Bodhi 则在系统层面多做了一层保护。两种思路都有道理，但我更倾向于后者——因为我希望在压缩发生时，系统的稳定性不完全取决于模型当次的表现。

### 它们代表的是四种不同的选择

我不觉得这四条路线谁一定比谁好。它们更像是同一个大方向上的不同选择：

- **Codex 选了模型优先**——把最强的模型能力直接给你用
- **Claude Code 选了产品优先**——把 Agent 体验做到极致顺滑
- **OpenClaw 选了开放优先**——让更多人用上类似体验
- **Bodhi 选了系统优先**——把 Agent 做成一个可理解、可控制、可长期运行的系统

而我选最后这条，不是因为它最好，而是因为**它最接近我想要的那个 Agent**。

如果要用一句更简洁的话来概括：

**Codex 和 Claude Code 让我看到了 Agent 已经能做到什么；OpenClaw 让我看到开源社区在努力追赶；Bodhi 则是在回答，我想把 Agent 设计成什么。**

---

## 我想把 Bodhi 做成什么

Bodhi 当然还在继续成长。它不是一个已经完成的终点。

但如果问我，今天我最想把它做成什么，我的答案已经比一开始清楚得多：

**我想把 Bodhi 做成一个真正可以进入工作流的 Agent 系统。**

不是只能短时间展示"智能感"的系统。不是只能在某个平台里被动使用的系统。也不是只能靠模型表现撑起一切的系统。

我想要的是一个：

- 有自己上下文架构的系统
- 有自己 agent loop 边界的系统
- 有自己 built-in tools 地基的系统
- 有 MCP 扩展能力的系统
- 有 skills 专业化工作模式的系统
- 同时又足够本地、足够可控、足够透明的系统

这也是我为什么会决定自己写它。

因为我越来越确信，未来真正有价值的 Agent，不会只是"更会说话"的 AI。它们更应该是那些**真正能长期工作、又始终保留人类控制权**的系统。

而这，正是我想把 Bodhi 做成的样子。
